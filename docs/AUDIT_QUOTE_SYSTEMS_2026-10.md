## 2. Findings

### Critical / High

**F1 [Certain] CRITICAL: A takeoff or field-sourced job can never be priced by the quote engine, and the first blocker is silent until the admin hits Send quote.**
`lib/pricing/quote-inputs.ts:92` derives `blankWidthIn` ONLY from `points` (FlashDraft polylines). Takeoff items carry `width/height/legA/legB` and no `points`, so `blankWidthIn = null` and `quoteFromPriceBook` returns `bad-blank-width` ("Open it in FlashDraft and check the drawing", `lib/pricing/quote-math.ts` ~lines 160-170). The file's own header says legA/legB are "Only read when there are no points" but nothing reads them. Meanwhile `approve-quote-request/route.ts` (~lines 239-258) happily computes `blankWidth = legA + width + legB` for the machine. So the machine can run a job the quote engine refuses to price. Field-photo jobs have `line_items: []` (`app/api/field/quote-request/route.ts:113`), so `toQuoteItemInputs` returns `[]` and nothing blocks pricing; see F11 for what that produces.
Impact: the entire "scan to quote" promise ends at "estimator prices by hand." This is the single biggest efficacy gap.

**F2 [Certain] HIGH: Quantity/length semantics are incompatible between the takeoff schema and the price engine.**
Takeoff prompt example: `lengthFt: 48, quantity: 1, unit: "LF"` (a run). Live test (b) returned `lengthFt 30, quantity 30`. The price engine treats `lengthFt` as a per-piece length and refuses anything over 10 ft (`quote-math.ts:181`, kind `bad-length`), and prices `sheetCost / strips x quantity` (whole pieces, `quote-math.ts:~205`). A 48 LF coping run therefore errors out, and a "quantity 30" would be priced as 30 pieces. There is no run-to-pieces conversion (ceil(LF / 10) with waste) anywhere.

**F3 [Certain] HIGH: `/api/takeoff` is unauthenticated, has no ownership check, and trusts a client-supplied `storageKey` with the service-role client.**
`app/api/takeoff/route.ts:152-154,195`: body `uploadId`, `storageKey`, `fileType` are used directly; `admin.storage.from('blueprints').download(storageKey)` runs with the service key. Nothing ties `storageKey` to the `takeoff_uploads` row for `uploadId`, and nothing checks the caller owns either. Consequences: (i) anyone who knows or guesses any object path in the `blueprints` bucket (paths are `blueprints/<userId|guest>/<uuid>/<name>`, so need the UUID) can have it sent to Anthropic and read back its extracted contents; (ii) anyone can burn Anthropic spend by POSTing the route repeatedly with any real storageKey (no rate limit, no per-upload "already processed" guard, no dedupe), and re-run a row's status/result (`:162`, `:343`); (iii) `fileType` is client-controlled and only sets the media type, never verified against the bytes (a PDF named .png yields an API error, not a security issue, but it is unvalidated). UUID entropy makes (i) hard, but (ii) is trivially exploitable for cost abuse. Same comment in `app/api/takeoff/[uploadId]/route.ts:6-11` accepts this trust model for PATCH; PATCH additionally accepts an unbounded `items` array of arbitrary JSON (no size or shape limit) written to `confirmed_items`.

**F4 [Certain] HIGH: The uploaded blueprint is never linked to the quote request, so the estimator cannot see the drawing the AI read.**
`app/api/quote-requests/route.ts` never writes `upload_id` (no `upload_id` anywhere in the file) and `app/upload/page.tsx:866-880` does not send `uploadId` in the body. The admin page comment (`app/admin/quote-requests/[id]/page.tsx:100-103`) claims both flows write `upload_id`; only the field flow does (`field/quote-request/route.ts:122`). `takeoff_uploads.request_id` is also never set. Result: a takeoff job reaches Command Center with AI-read line items, no drawing, and no way to verify an AI value against its source. The "What the AI read" panel (`lib/ai/takeoff-confidence.ts`) is fed from `result_items`, which are also unreachable from the job without that link.

**F5 [Certain] HIGH: AI confidence and "default vs read" provenance are lost at submit.**
`app/upload/page.tsx:783` runs `applyStandardDefaults` (fills width/height/legs/material/gauge from `STANDARD_PROFILE_DEFAULTS`, `lib/data/catalog.ts:694-707`, e.g. "Galvanized Steel / 24 ga" for everything). The UI badges them, but the submitted `items` (`:866`) carry no `prefilled` marker, and `confidence` stays whatever the model said for the item ("high") even though the material/gauge were defaulted by AFS. Downstream the price-book lookup key is material+gauge, so a silently defaulted "24 ga galvanized" produces a confident-looking price on a guess. The panel-width rule in the prompt (never guess) is therefore partly undone by a second, client-side layer that does guess.

**F6 [Certain] HIGH: Model output is persisted/forwarded with no schema validation; one bad parse loses the whole read.**
`takeoff/route.ts:314` `JSON.parse(clean)` inside the outer try: any malformed or truncated output becomes `status:'failed'` and HTTP 500 "Processing failed", and the customer has paid the latency and the model cost for nothing. `stop_reason` is never checked: `max_tokens: 8000` (`:289`) with ~150 output tokens per item means roughly 50 items before truncation; a big CD set (the prompt asks for "every distinct occurrence" across up to 100 pages) will hit it, truncating the JSON mid-array. `result.items` is stored (`:344`) and returned (`:353`) raw; item fields (`lengthFt`, `quantity`, `confidence`) are not type-checked (only `overallConfidence` is normalised, `:325`). `quote-requests` validates only `profileType/lengthFt/quantity` and silently drops the rest (F9).

**F7 [Likely] HIGH: Long jobs will exceed the 300 s function limit and strand state.**
No `maxDuration` is set anywhere (no `export const maxDuration` in `app/api/takeoff`, none in `vercel.json`/`next.config`). Live test took 12-14 s for tiny inputs; a multi-page PDF read through Files API plus an 8000-token generation will plausibly take 60-200 s, and the SDK client (`lib/anthropic/client.ts`) uses the SDK default 10-minute timeout, which is longer than any Vercel limit. When the function is killed: row stays `status:'processing'` forever (set at `:162`, only cleared in the catch), and the Anthropic Files API upload is orphaned because the `finally` that deletes it (`:305-310`) never runs. The browser `fetch('/api/takeoff')` has no timeout/abort and no polling (`app/upload/page.tsx:765`), so the user stares at a spinner. Also PDF page limit is 100 (`lib/utils/upload-limits.ts`), which is Anthropic's own PDF page cap; a dense 100-sheet set can exceed the model context. [Guessing] on the exact context failure threshold.

**F8 [Certain] HIGH: Field flow never calls AI and sends no confirmation, but tells the customer it will.**
`app/api/field/quote-request/route.ts` creates a quote_request with `line_items: []` and `source_tool: 'field_photo_quote'` and never calls `/api/takeoff` or any model (comments at `photo-upload/route.ts:6-12` confirm that was a deliberate decision). So "photo-to-quote" is currently "photo-to-inbox": a human reads every photo. `ContractorCameraQuoteForm.tsx:349` says "Enter your email so AFS can send your quote confirmation", but the route sends no email at all (contrast `quote-requests/route.ts:221`). The form also collects no phone number, no jobsite address/location, no size/length cue, and no "what is this" question, so even the human has little to quote from. `SPEC_PHOTO_TO_QUOTE_AI` implies AI; the title says AI; the code has none.

### Medium

**F9 [Certain] MEDIUM: `quote-requests` silently drops invalid items and accepts unbounded, unvalidated input.**
`quote-requests/route.ts:86` `items = rawItems.filter(isValidItem)`: any item with `lengthFt` null (which the model legitimately emits when a length is not on the drawing, see prompt "set that field to null") or `quantity` null is dropped without telling the customer, and the request still succeeds as long as one item survives. No cap on item count or string lengths, `projectId` (`:107`) and `jobsiteAddress` (`:108`) are stored without type or ownership check, `line_items` stores the raw client objects (arbitrary extra keys, including prompt-injection text in `aiNote`/`profileType` that later reaches the admin screen, the quote email description (`describeQuoteLine` uses `profileName`/`profileType` verbatim) and the PathfinderEdge title). No rate limit or CAPTCHA on a guest-open endpoint that writes DB rows and sends mail.

**F10 [Certain] MEDIUM: Guest email abuse and HTML injection in the confirmation mail.**
`quote-requests/route.ts:99,221-232`: a guest can submit anyone's address and AFS sends a branded email to it (spam/relay and reputation risk). `recipientName` comes from the profile and is interpolated into HTML un-escaped (`:226`) (low risk since it is the user's own profile name, but unescaped). Field route sends none (F8).

**F11 [Likely] MEDIUM: Empty-line-item jobs may produce a $0 "quote".**
`priceJob` on `line_items: []` yields `quoteFromPriceBook([], book)` which, reading `quote-math.ts`, loops zero items, finds zero problems and returns `ok:true, lines:[], totalCents:0`. `issueQuoteForJob` then inserts a quote of $0, emails it with an Approve link, and moves the job to Quoted. The field-photo job is exactly this shape until an estimator adds lines. I did not execute this path against a live DB. A guard ("at least one line") is needed in `issueQuoteForJob`.

**F12 [Certain] MEDIUM: Field photo ownership check lets any guest attach any guest upload.**
`field/quote-request/route.ts:86`: for a guest, ownership = `user_id IS NULL`, i.e. ANY guest-created upload row matches; there is no secret binding the upload to the submitter and no check that an upload is not already attached to a different request, or that the Storage object actually exists (the comment at `:92-95` says the status update "confirms the PUT landed" but it only flips a flag). UUID unguessability is the only protection, and a leaked/shared link attaches someone's jobsite photos. Same row can back several requests.

**F13 [Certain] MEDIUM: File validation is extension-only everywhere.**
`api/upload/route.ts:51-54` and `field/photo-upload/route.ts:56-60` check extension and the client-claimed `fileSize`; neither signed-URL route constrains the actual bytes (Supabase signed upload URLs do not enforce size or MIME unless the bucket is configured to). Takeoff does re-check size and PDF parse (`:208-248`), but the field flow never inspects the file at all, and stored `content-type` is whatever the client sets. No malware or magic-byte check; admin gets a signed URL to the original (`app/admin/quote-requests/[id]/page.tsx:124`).

**F14 [Certain] MEDIUM: Unsupported-but-accepted formats dead-end.**
UI and sign route accept `.dwg .dxf .tiff .tif` (`upload-limits.ts`, `page.tsx:1080`), but takeoff only handles png/jpg/jpeg/webp/pdf (`takeoff/route.ts:166-167`) and returns `status:'partial'`, `items: []` with a "require conversion" note after the user has already uploaded up to 50 MB. The page treats an empty result as `failed` (`page.tsx:~790`). TIFF is easy to convert server-side; DWG/DXF can be parsed (DXF) or rejected at the sign step. HEIC is accepted by the field flow (`field-photo-limits.ts`) but never converted: the field form re-encodes via canvas (`ContractorCameraQuoteForm.tsx:67-80`) which only works where the browser can decode HEIC; and the original HEIC would not render in a non-Safari admin browser. Takeoff would reject HEIC outright if the field flow ever called it.

**F15 [Certain] MEDIUM: Quote issuance is not atomic and has race/orphan windows.**
`lib/quotes/issue.ts`: quote number = max()+1 with no lock (`:91-105`, used at `:177`), two admins sending at once collide or fail on the unique constraint (same pattern in `quote-requests/route.ts:60-70` for request numbers: two simultaneous submissions can get the same AFS-QR number and one will 500 "Submission failed"); the quote is inserted with `status:'sent'` (`:188`) BEFORE the email is attempted (`:271`) and before the token insert; if the token insert fails the quote row stays `sent` with no approve link (`:233-243`); if email fails the job still advances to Quoted (`:290-300`) (arguably intended, message says so). Revision supersede + token expiry run as separate non-transactional updates.

**F16 [Certain] MEDIUM: Quote totals omit rush, finish/color, freight and tax by design, with no visible "estimate" labelling.**
`issue.ts:195` `rush_surcharge: 0`; `quote-math.ts:~245` says freight and tax are open data blockers and totals equal subtotal. `is_rush` is passed to the ledger but never priced. Color/finish chosen in the takeoff table (`page.tsx:buildRequestColor`) never affect price (the price book key is material+gauge only). Fine as a deliberate stage, but the customer email presents a "total" with no stated exclusions unless `email-template.ts` does (not verified).

**F17 [Likely] MEDIUM: Material/gauge string matching between AI output and the price book is brittle.**
`quote-math.ts:77,110` matches `material|gauge` lowercase-trimmed exact. The price book rows come from the `materials`/`gauges` catalog labels (migration 035 seed, `INSERT ... SELECT m.name, g.label`). The model returns "Galvanized Steel"/"20 ga" in one run and "Aluminum"/".040" or `.032"` in others (live test a, b). Any mismatch yields `no-price-book-row` (an error, not a wrong price, so safe but a constant source of friction). The prompt does not constrain material or gauge to the catalog vocabulary; the client does not normalise AI strings to catalog values before submit.

### Low

**F18 [Certain] LOW:** `pagesProcessed: 1` is hard-coded (`takeoff/route.ts:355`) even for a 60-page PDF; `page_count` is only stored for PDFs. Diagnostic `console.log` blocks marked "temporary" remain (`:261`, `:331`) and log the first 500 chars of model output and storage paths.
**F19 [Certain] LOW:** `scopeDirective.customText` is interpolated into the system prompt un-sanitised (`takeoff/route.ts:~42`) and is unbounded: a customer can inject instructions into the system prompt. Blast radius is limited to their own extraction, but it can suppress items or change `quantity`, and what the model returns is then trusted into line_items.
**F20 [Certain] LOW:** No retry/backoff beyond the SDK default (2 retries on 429/5xx), no idempotency: a double click or browser retry re-uploads to the Files API and re-runs the model (cost) with the same uploadId.
**F21 [Certain] LOW:** `takeoff_uploads.confirmed_items` (user-corrected items) is written by the debounced PATCH but nothing reads it, and `request_id` is never set; there is no `takeoff_corrections` table in any migration. The data needed for calibration exists only per upload row and is not joined to the final quote.
**F22 [Certain] LOW:** `roof panel` (`calculatedAreaSqFt`) is handled client-side by `calculatePanelQuantity`, but the engine has no price model for standing seam panels (price book is sheet-cut flashing; panels are priced by area/LF). A roof panel item reaching `priceJob` will fail with blank-width.

## 4. Innovative upgrades (not defects)

1. **Scale and fiducial calibration for photos.** Ask the contractor to place a standard object in frame (tape measure, a printed AFS 12" card with a QR/ArUco marker, or a framing square). Detect it, compute px/in, and have the model (or classic CV) return measured legs and girth with an error bar. Without a reference, the model should return dimensions as null (the prompt already supports this); with one, the field flow becomes a real quote path.
2. **Two-pass verification.** Pass 1 extracts; pass 2 (cheaper model or same model with the image + JSON) is asked only "for each item, quote the text/dimension string that supports each field and say contradiction yes/no". Items with unsupported fields are downgraded to low; the contradiction check would also catch the (a) `height` vs legs duplication.
3. **Confidence calibration from real corrections.** `confirmed_items` vs `result_items` already hold the human edit signal, but nothing links them to outcomes. Add a `takeoff_corrections` table (field, ai_value, final_value, confidence, profile_type, source type) populated at submit and at quote send; compute per-field accuracy per confidence bucket and replace the model's self-reported "high" with an empirically calibrated score (it said "high" on a tilted, blurred sketch).
4. **Drawing-aware cropping.** For large sets, run a cheap first pass to classify sheets (details / plans / schedules), then send only detail sheets at higher resolution; cuts cost and avoids the 8000-token ceiling.
5. **Structured outputs and tool-use.** Replace "RETURN ONLY valid JSON" prompting with a tool schema (`tool_choice` forced) so the SDK returns validated JSON and fences/parse errors disappear.
6. **Price from history.** The pricing ledger already records every issued quote line; use nearest-neighbour lookups ("last 5 jobs for this customer with similar girth") to show the estimator a sanity range beside the computed price.
7. **Customer-facing loop.** Show the customer the AI reading over their own drawing (boxes on the image) and let them correct before submitting; every correction becomes calibration data (#3).

## 5. What is solid (so it is not "fixed" by mistake)
- The takeoff prompt follows its own rules in live tests: null-vs-guess on panel width, slope math (894 vs exact 894.4), seam-type default flagged, honest empty result on irrelevant input.
- Quote engine refuses blanks, over-width, over-length and never treats blank as zero; snapshots and revision chain are sound (`lib/quotes/issue.ts`, `lib/pricing/quote-math.ts`); admin routes check session plus `role = admin` (`send-quote`, `admin/quote-requests/[id]`); the Files API upload is deleted in `finally` on the normal and error-return paths.
- Rush is never inferred (`quote-requests/route.ts:109-118`, migration 034 CHECK).
